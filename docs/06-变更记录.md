# 变更记录

## 2026-08-22 上线安全加固

### 目标与范围

本次改造处理公网发布前的认证安全、信息暴露、健康检查、生产构建、日志生命周期、数据库备份恢复和测试缺口。代码继续遵守 `frontend/`、`backend/`、`docs/` 平级结构，以及单个 NestJS 服务同时提供 API 和前端产物的部署架构。

### 管理员密码与迁移

管理员密码改用 bcrypt cost 12 哈希。数据库仍保留 `password` 字段名以兼容现有结构，但实体、`backend/database/schema.sql` 和 `docs/schema.sql` 均把字段语义改为 bcrypt 密码哈希。登录不再直接比较新密码。

为兼容已有数据库，登录服务会识别非 bcrypt 格式的旧密码。旧密码首次验证成功后，在同一登录流程中立即计算并保存 bcrypt 哈希，因此不需要导出旧密码，也不会继续长期保留明文。

生产模式执行迁移时必须显式提供 `INITIAL_ADMIN_USERNAME` 和 `INITIAL_ADMIN_PASSWORD`，缺失时在连接数据库前中止。只有本地模式保留 `admin` 默认值，且写入数据库的仍是哈希。管理员已存在时，迁移会更新密码哈希和显示名，因此修改 Secret 后重新迁移可以完成密码轮换。轮换后还应注销或清理旧会话。

迁移脚本允许 `.env.production` 不存在，配置优先取进程环境变量，因此可以只使用托管平台 Secret。

### 登录防暴力破解

登录接口按“真实客户端 IP + 规范化用户名”组合记录失败。连续失败 5 次后封禁 15 分钟，成功登录会清除该组合的失败记录。记录保存在当前进程内，符合目前单实例定位。

公网仍必须在 Cloudflare、Nginx 或托管平台配置第二层限流。未来改为多实例时，应将计数迁移到 Redis 或数据库，以便实例间共享。

### HTTP 安全与错误响应

应用加入 Helmet，并明确 CSP：默认资源、脚本和连接只允许同源，禁止对象嵌入和第三方 frame；Chakra UI 运行时样式需要 `style-src 'unsafe-inline'`。上线冒烟时应检查浏览器控制台，确认没有 CSP 违规。

生产环境未知 5xx 异常统一返回“服务器内部错误”，原始异常、堆栈和数据库错误只写脱敏日志。4xx 业务错误继续返回可操作信息。

生产环境默认不创建 Swagger 页面及文档 JSON。只有显式设置 `ENABLE_SWAGGER=true` 才启用，该开关只应在受控网络临时使用。

### 健康检查与反向代理

新增两个无需登录的探针：`GET /api/health` 只检查 Node.js 进程响应；`GET /api/ready` 执行 `SELECT 1` 检查 MySQL，失败返回 HTTP 503。负载均衡器的存活探针使用前者，接流量前的就绪探针使用后者。

两个探针均已加入 Swagger 的“健康检查”分组，文档包含用途说明、统一成功响应结构，以及数据库不可用时的 HTTP 503 响应。生产环境仍默认不生成 Swagger。

Express `trust proxy` 由 `TRUST_PROXY_HOPS` 控制，默认信任一层代理。反向代理必须覆盖写入 `X-Forwarded-For` 并丢弃客户端伪造值。代理层数变化时必须同步调整，否则日志和登录限流会识别错误 IP。

### 生产构建、页面与 SQL 日志

Vite 只在非 production 模式输出 source map，正式根目录构建不会再发布 `.map` 文件。HTML 语言改为 `zh-CN`，标题改为产品名，并增加产品描述。

TypeORM 本地继续记录完整 SQL 以便调试，生产只记录 `error` 和 `warn`，降低敏感参数暴露及磁盘增长风险。

项目通过 `.node-version` 和三个 `package.json` 固定 Node.js 22。`install:all` 改为对子项目执行 `npm ci`，所有环境均按 lockfile 可复现安装。

### 日志保留和磁盘告警

应用继续按每次启动创建带日期和序号的新日志文件。启动时只清理符合 `jvs-YYYY-MM-DD-NNN.log` 命名且超过 `LOG_RETENTION_DAYS` 的文件，默认保留 30 天，不会删除其他文件。

启动时检查日志磁盘可用比例；低于 `DISK_FREE_WARN_PERCENT`（默认 10）会输出警告。生产平台必须抓取该警告，并另设磁盘使用率监控与通知联系人。应用内警告不能代替外部告警，因为磁盘写满时应用可能无法继续记录。

### 数据库备份和恢复

`npm run db:backup` 调用 `mysqldump`，使用单事务模式并包含 routines 和 triggers，输出到被 Git 忽略的 `backend/backups/`。密码通过子进程环境变量传递，不进入命令行参数或日志。

`npm run db:restore -- CONFIRM_RESTORE <file>` 调用 MySQL 客户端恢复。脚本只接受 `backend/backups/` 内的文件，并要求显式确认。建议每天自动备份、异地加密复制、保留日/周/月多个周期；每季度在隔离数据库恢复并验证管理员登录、知识库、题库进度和关键表行数。全量同步仍是人工高风险工具，不属于备份流程。

### 测试补充

新增登录组合限流测试，覆盖五次失败封禁、不同 IP 隔离和成功后清除记录。新增基于 Nest 测试应用与 Supertest 的健康端点集成测试，覆盖进程存活、数据库就绪以及数据库失败返回 503。

上线前还要在连接测试 MySQL 的环境执行 API/e2e 测试，并人工验证登录、退出、权限、主要 CRUD、深层 React 路由刷新、题库答题、备份及恢复。生产迁移与恢复不得绑定普通构建或启动流程。

### 生产配置清单

必须通过平台 Secret 提供数据库连接、`INITIAL_ADMIN_USERNAME` 和强随机 `INITIAL_ADMIN_PASSWORD`。建议同时明确设置：

- `NODE_ENV=production`
- `PORT=3000`
- `TRUST_PROXY_HOPS=1`
- `ENABLE_SWAGGER=false`
- `AUTH_SESSION_DAYS=30`
- `LOG_RETENTION_DAYS=30`
- `DISK_FREE_WARN_PERCENT=10`

首次发布顺序为：创建最小权限数据库账号，执行备份，运行生产迁移，执行可复现安装和根目录构建，启动服务，等待 `/api/ready` 成功，再接入流量并完成冒烟测试。任何 `.env`、备份、密码和令牌都不得提交。

## 2026-08-22 本地数据库全量覆盖线上

按人工明确授权执行生产数据库全量覆盖。目标确认结果为本地 `127.0.0.1/daziwordsapp`、线上 Aiven `daziwordsapp`，两者不是同一实例，线上地址也不是本机地址。

执行前使用官方 MySQL 8.4 临时客户端完整备份线上数据库，并完整导出本地数据库。首次按逐表 drop 顺序恢复时，线上尚未删除的旧父表与本地子表外键发生临时类型冲突，恢复中止。随后保留原始备份，不移除任何外键，改为先关闭外键检查并一次性删除线上全部视图和数据表，再从未修改的本地 dump 恢复。

最终恢复成功，并通过只读校验脚本比较本地与线上正式数据表清单及每张表的精确行数：两端均为 44 个数据表，合计 3927 行，未发现行数差异。覆盖前原始线上备份为 `backend/backups/online-before-sync-2026-08-22T13-22-27.641Z.sql`；备份目录被 Git 忽略，不得提交。

## 2026-08-22 Vercel 部署适配

应用采用前后端两个 Vercel 项目：`backend/` 由 Vercel 原生 NestJS 支持部署为单个 Node.js Function，`frontend/` 作为 Vite 静态站点发布，并通过同源 `/api` Rewrite 访问后端。数据库继续使用 Aiven MySQL。

Vercel 环境不再加载 Nest 静态文件服务，也不向临时文件系统写运行日志；HTTP、数据库、业务和异常日志改为标准输出，由 Vercel Observability 收集。本地和普通长驻服务器仍保留原有静态托管及文件日志行为。后端 Function 区域优先设置为东京 `hnd1`，减少与日本区域数据库之间的网络延迟。

后端生产项目为 `dazi-projects/japanese-vocabulary-api`，固定域名为 `https://japanese-vocabulary-api.vercel.app`。由于 TypeORM 在运行时动态加载 MySQL 驱动，Vercel Function 使用显式 `api/[...path].js` 入口，并把 Nest `dist/` 和 `mysql2` 纳入函数追踪范围。线上 `GET /api/health` 返回 `ok`，`GET /api/ready` 返回 `ready`，确认进程与 Aiven MySQL 连接正常。

前端生产项目为 `dazi-projects/japanese-vocabulary-study`，固定域名为 `https://japanese-vocabulary-study.vercel.app`。`frontend/vercel.json` 将 `/api/:path*` 重写到后端固定域名，并把其他路径重写到 `/index.html`。线上已验证 `/api/health` 同源转发成功，直接刷新 `/login` 能返回 SPA 页面。

项目所有者随后明确批准公开网站，已关闭前后端两个生产项目的 Vercel SSO Deployment Protection。使用不带团队绕过令牌的公网请求完成最终验证：首页、`/login`、`/api/health` 和 `/api/ready` 均返回 HTTP 200，页面标题、SPA 容器、进程状态和数据库就绪状态均符合预期。应用自身的管理员登录、会话 Cookie 和登录限流继续作为业务访问控制。

公开后发现最初的 Vercel Catch-all 文件路由只能稳定命中单层 API 路径，`POST /api/auth/login` 这类多层路径由平台返回 404。后端改为通过 Rewrite 将所有 `/api/:path*` 统一交给 `api/index.js` 单一函数入口，同时保留原始 URL 供 Nest 路由匹配。重新发布后，通过前端公开域名验证健康接口返回 HTTP 200，登录接口返回 HTTP 201、业务 `success: true`，并成功下发会话 Cookie。

公开冒烟后按项目所有者要求轮换线上管理员凭据。新增人工高风险命令 `npm run admin:rotate --prefix backend`：必须提供显式确认、旧用户名、新用户名和至少 16 位的新密码；脚本在单个数据库事务内锁定管理员记录、检查用户名冲突、保留原数据库 ID、更新用户名和 bcrypt cost 12 密码哈希，并撤销该用户全部有效会话。密码只通过进程环境变量和 Vercel Sensitive Secret 传递，不写入代码、Git 或文档。

本次线上轮换撤销了 17 个历史会话，并将生产初始管理员用户名和密码同步保存为 Vercel Production Sensitive Secrets。重新部署后验证：旧账号返回 HTTP 401；新账号登录返回 HTTP 201；`/api/auth/me` 返回新用户名；测试会话随后成功退出。
